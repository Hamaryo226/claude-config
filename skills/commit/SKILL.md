# コミットする

未コミットの変更を読んで、意味のある単位に分けてコミットする。**push はしない。**

## 手順

### 1. 現況を把握する

```bash
git status --porcelain
git diff
git diff --staged
git log -5 --pretty=format:'%s'
```

`git log` は、そのリポジトリのメッセージの書き方を確認するために必ず見る。

### 2. 論理単位に分ける

変更を「1 つのことをしている塊」に分ける。分ける基準:

- 機能追加 / バグ修正 / リファクタリング / 整形だけの変更 は別コミット
- 実装とその実装に対応するテスト・ドキュメントは**同じ**コミットでよい
- 無関係なファイルを 1 つのコミットに混ぜない

分け方を決めたら、コミットする前にユーザーに提示して確認を取る。1 コミットで済むと明らかな場合は、
確認を省いてそのまま進めてよい。

### 3. ステージしてコミットする

塊ごとに `git add <具体的なパス>` する。`git add -A` や `git add .` は使わない。

メッセージの規約 (このユーザーの既存リポジトリの流儀):

- **日本語・1 行・prefix なし**
- `feat:` `fix:` のような Conventional Commits 形式は**使わない**
- 「何をどう変えたか」を書く。「修正」「更新」だけの中身のないメッセージにしない
- 実例: `連打の終わりが無い譜面で落ちるのを直す` / `期間ごとのcsv,xlsxをエクスポートできる機能追加` /
  `リザルトを責務ごとの partial に分け、AIバトルのぶんを切り離す`
- そのリポジトリの `git log` が別の流儀 (英語、Conventional Commits など) ならそちらに合わせる

補足が要るときだけ、空行を挟んで本文を書く。

### 4. 結果を報告する

```bash
git log --oneline -<コミット数>
git status --porcelain
```

## 守ること

- **push しない。** 求められても、このスキルの範囲外だと伝える
- `main` / `master` に居るときは、コミットする前に警告してブランチを切ることを提案する
- `--no-verify` は使わない。pre-commit フックが落ちたら、原因を直すか報告する
- `.env` や鍵ファイルらしきものがステージされそうなときは止めて確認する
- 生成物 (`bin/` `obj/` `dist/` `node_modules/`) が入っていたら、`.gitignore` の漏れとして報告する
