# 既存プロジェクトの設定を見直す

成功条件は、そのリポジトリ特有の判断に必要な情報を、適切な範囲で参照できること。
単純な導入は onboard、コード慣習の抽出だけなら codebase-conventions を使える。
通常のコード修正を全体の設定監査に広げない。

## 調査と判断

- 依頼範囲の既存指示と根拠を読む。設計資料は意図、実装・テストは現状、CI は実行条件の証拠として使い分ける。矛盾は一律の優先順位で消さない。
- 必要な資料を探すときは [discovery.md](references/discovery.md) の該当項目だけを使う。全項目を埋める必要はない。
- 配置する層の判断には [decision.md](references/decision.md) を使う。既存の有用な規約・境界を残し、重複や根拠のない一般論を整理する。
- 読めない資料や解決できない仕様差は、その判断への影響を短く報告する。資料がないだけで実装から確認できる事実まで捨てない。

## 改善

変更箇所と理由を短く示す。改善まで依頼されていれば、既存内容を確認したうえで編集・検証まで進める。
分析・提案だけなら報告で終える。結果を左右する未解決の仕様や依頼範囲の拡大は確認する。

新規生成の形式が必要なら [templates.md](references/templates.md) を参照する。
AGENTS.md / CLAUDE.md / rules に同じ指示を複製せず、資料は必要になる条件とともにリンクする。
配置先に存在しない評価記録や別スキルに依存させない。

指示の適用範囲、リンク、設定形式と記載コマンドの根拠を確認する。
実行が必要な検証だけを選び、未実行と実行成功を区別する。最終報告は変更理由と未解決事項を中心にする。
