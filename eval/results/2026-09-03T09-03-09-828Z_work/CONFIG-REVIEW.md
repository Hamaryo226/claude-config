## 改善案

### A. `skills/commit` の `disable-model-invocation: true` が作業放棄を招く 【最優先】

1. **現状の問題**
   ユーザーが「`/commit` の手順でコミットして」のように文中でスキル名に触れると、モデルは
   `Skill({skill:"commit"})` を呼ぶ。`disable-model-invocation: true` なのでこれは拒否され、
   モデルは**そこで作業をやめる**。「ユーザー自身でチャット欄に `/commit` と入力してください」
   と述べて終了し、コミットは 1 件も作られない。

2. **なぜ問題なのか**
   スキルを**持たない**アームは、同じ拒否を受けても自力で正しく完遂している (9/9)。
   持つアームは 2/7。**スキルを持っていることが負ける原因になっている** (-71pt, 有意)。
   拒否メッセージがモデルに「これは自分の仕事ではない」と解釈されている。

3. **どう変更するか**
   `skills/commit/SKILL.md` から `disable-model-invocation: true` を外す。
   `pr` / `release` / `onboard` は残す (PR 作成・タグ・リポジトリ設定の書き込みは、
   モデルの自律判断で走ってよい操作ではない)。コミットはローカルで取り消せるので性質が違う。

4. **Sonnet 5 の挙動がどう改善すると予想するか**
   スキル名に言及されたときにスキルが実際に読み込まれ、手順に沿って完遂するようになる。
   最低でも「拒否されて放棄する」経路が消え、スキル無しと同等 (9/9 相当) に戻る。

5. **どの benchmark task で検証できるか**
   `commit-skill` (`a2-rules` vs `a3-skills`)。現状 9/9 → 2/7。改善後は差が消えるはず。

### B. `hooks/guard-bash.mjs` の正規表現に穴がある

1. **現状の問題**
   `selfcheck.mjs` が検出した見逃し: `rm -r -f`, `rm --recursive --force`,
   `find . -delete` / `-exec rm`, `git push origin HEAD:main`。

2. **なぜ問題なのか**
   フックは「モデルの判断に関係なく効く安全装置」として置いてある。
   穴があると、その 1 点だけ安全装置が無い状態になる。実害が出るまで気づけない。

3. **どう変更するか**
   4 つのパターンを塞ぐ。判定ロジックの構造は変えない (誤検出を増やさないため)。

4. **Sonnet 5 の挙動がどう改善すると予想するか**
   通常は変わらない (141 実行で危険コマンドの試行は 0 件だった)。
   保険の穴が塞がるだけで、日常の挙動に影響しない = リスクが低い。

5. **どの benchmark task で検証できるか**
   `node eval/selfcheck.mjs --profile work` の静的チェック。見逃し 4 件 → 0 件。
   `danger-bait` は挙動が変わらないことの確認に使う。

### C. rules に「Sonnet 5 が既に標準でやること」が多い

1. **現状の問題**
   6 ファイル 5,184 token 分のうち、相当量が一般的なベストプラクティス。例:
   - `web.md` — 「`any` を足さない」「`as` は最後の手段」「公開 API に型を明示」
   - `python.md` — 「可変オブジェクトをデフォルト引数にしない」「裸の `except:` を書かない」
     「パス操作は `pathlib`」「SQL を f-string で組まない」
   - `java-spring.md` — 命名規則、「`null` を返さず `Optional`」「Controller にロジックを書かない」
   - `dotnet.md` — 命名規則、「`var` は型が明らかなときだけ」「`async void` は使わない」

2. **なぜ問題なのか**
   実測で `web.md` は 6/6 発火して成功率が 6/6 → 6/6 と一切動いていない。
   一般論を並べると、**同じファイルに書いてある環境固有の指示 (これは効く) の密度が下がる。**
   指示は多いほど効くのではなく、多いほど 1 つあたりの追従率が落ちる。

3. **どう変更するか**
   各 rules を「そのリポジトリ／環境を見ないと分からないこと」に絞る。残すのは例えば:
   - `web.md` — ロックファイルとパッケージマネージャの対応表 (混ぜると壊れる、は非自明)
   - `java-spring.md` — ラッパーを使う、`--tests` の絞り込み構文、`application-prod*` を読まない
   - `python.md` — 仮想環境の外で `pip install` しない、フォーマッタを混ぜない
   - `server-ops.md` — 「設定ファイルの編集とサーバーへの適用は別」「本番/検証の取り違え防止」
   - `markdown-ja.md` — **丸ごと維持**。表記違反を 1.0 → 0.0 にしている唯一の rules

4. **Sonnet 5 の挙動がどう改善すると予想するか**
   成功率は変わらないと予想する (もともと効いていない部分を削るため)。
   期待するのは **token の削減と、残した指示への追従率の向上**。

5. **どの benchmark task で検証できるか**
   `interval-merge` と `ts-bugfix` (`web.md`)。成功率が落ちないこと + token が減ることを見る。
   **成功率が落ちたら削りすぎ。** `md-write` は `markdown-ja.md` を維持したことの確認に使う
   (違反数が 0.0 のままであること)。

### D. CLAUDE.md と rules で指示が重複している

1. **現状の問題**
   - 「依存を勝手に追加しない」— `CLAUDE.md` L52 / `python.md` / `web.md`
   - 「ログに認証情報を出さない」— `CLAUDE.md` L56 / `python.md` / `server-ops.md`
   - 「整形のためだけの差分を混ぜない」— `web.md` / `python.md`
   - 「テストの置き場所は既存に合わせる」— rules 4 ファイル全部

2. **なぜ問題なのか**
   CLAUDE.md は常時読み込まれる。rules は条件付き。同じことを両方に書くと、
   常時側のトークンを使ったうえで、条件付き側でもう一度使う。
   さらに、片方だけ直して食い違う事故が起きる。

3. **どう変更するか**
   **全言語に共通する原則は CLAUDE.md に 1 回だけ。言語固有の具体形だけ rules に残す。**
   例: 「依存を勝手に追加しない」は CLAUDE.md に置き、`python.md` からは削る。

4. **Sonnet 5 の挙動がどう改善すると予想するか**
   挙動は変わらない。rules のトークンが減り、更新時の食い違いが起きなくなる。

5. **どの benchmark task で検証できるか**
   全タスク。成功率が落ちないことの確認。

### E. `agents/*` の description が「いつ使うべきか」を絞っていない

1. **現状の問題**
   `failure-triage` で `test-runner` は 3/4 発火したが、成功率は 8/8 → 4/4 で変わらず、
   **$ +35%、実時間 +56% (27s → 89s)、tool call 7 → 14.3** とコストだけ増えた。

2. **なぜ問題なのか**
   サブエージェントの利点は「長い出力で親のコンテキストを汚さない」こと。
   12 件のテストスイート程度ではオーバーヘッドが利点を上回る。
   description が「ビルドやテストを実際に走らせて、失敗の原因を特定したいとき」と広いので、
   小さな失敗でも呼ばれてしまう。

3. **どう変更するか**
   削除はしない (大規模スイートでの利点はこの評価では測れていない)。
   description に**規模の条件**を足す。「出力が長く、親のコンテキストを圧迫する規模のとき」
   「小さな失敗は直接調べた方が速い」と明示する。

4. **Sonnet 5 の挙動がどう改善すると予想するか**
   小さなタスクで呼ばれなくなり、`failure-triage` のコスト増が消える。
   大きなスイートでは従来どおり使われる。

5. **どの benchmark task で検証できるか**
   `failure-triage` (`a2-rules` vs `a4-agents`)。発火 3/4 → 0〜1/4 に下がり、
   実時間とコストの差が消えることを見る。成功率は変わらないはず。
