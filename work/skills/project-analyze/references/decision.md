# 層の振り分け判断

Phase 2 で使う。**既定は「作らない」。** 下の関門を全部通ったものだけ作る。

## 全候補に共通の関門

順に問う。1 つでも当てはまったら作らない。

1. **Sonnet 5 が既に標準でできることか** — できるなら作らない。
   例: 「テストを書く」「`null` を返さず `Optional`」「裸の `except:` を書かない」「命名規則」
2. **コードを読めば 1 分で分かることか** — 分かるなら作らない。
   例: ディレクトリ一覧、依存一覧、クラス構成
3. **ユーザーの `~/.claude` や会社共通設定に既にあるか** — あるなら作らない。
   例: 応答言語、コミットメッセージ規約、`git reset --hard` の禁止、OS とシェル
4. **裏が取れているか** — コードからの推測だけなら作らない。設計資料か CI で確認する
5. **この一文が無いと Claude が実際に間違うか** — 想像できないなら作らない

通ったものだけ、次で層を決める。

## CLAUDE.md — 常時読み込み

**全セッションで必ず要るプロジェクト固有情報だけ。** 常時トークンを消費するので最も基準が厳しい。

入れる:

- build / test / run のコマンドと、CI で必須のチェック
- アーキテクチャ上の重要な制約 (破ると動かない、レビューで必ず差し戻されるもの)
- 絶対に触ってはいけないもの (生成コード、秘匿ファイル) と、その再生成手段
- このプロジェクト固有の Git ブランチ運用・リリース制約

入れない:

- 一般的なプログラミングのベストプラクティス
- 特定のディレクトリでしか要らない話 (→ rules)
- 手順が 3 ステップ以上ある作業の中身 (→ skill。CLAUDE.md には skill の存在すら書かなくてよい)

分量が増えるほど 1 つあたりの追従率が落ちる。**上限 120 行。**超えるなら rules に逃がすのではなく、まず削る。

## .claude/rules/ — 条件付き読み込み

`paths` フロントマターに一致するファイルを読んだときだけ載る。**paths を書けないなら rules にしない。**

作る条件 (全部満たすこと):

- 対象が特定のディレクトリ・ファイル種別に限られる
- そのファイルを触るときに毎回効く (たまにしか効かないなら Skill か、書かない)
- CLAUDE.md に同じことを書いていない

実測で効いたのは「機械的に判定できて、違反が数えられるルール」(表記・命名の統一など)。
効かなかったのは「一般論を並べたファイル」。**1 ファイル 60 行以内**を目安にする。

設計資料から抽出したルールが実装と矛盾している場合、**どちらかを正解として書かない。**
矛盾として報告し、ユーザーが決めてから書く。

## .claude/skills/ — 明示的に起動

**繰り返し発生する、プロジェクト固有の複数ステップ作業だけ。**

作る条件 (全部満たすこと):

- 手順が 3 ステップ以上あり、順序を間違えると壊れる
- git 履歴か運用手順に、**3 回以上繰り返された痕跡**がある
- 手順の中にプロジェクト固有の情報 (コマンド、採番規則、更新対象ファイル) が含まれる

例: API 追加 (仕様更新 → 生成 → 実装 → テスト → 仕様書反映)、DB migration、リリース手順、
コード生成、特定形式の設計書更新。

作らない:

- 「Java を書く」「テストを書く」のように Sonnet 5 が標準でできる作業
- ステップが実質 1〜2 個のもの (CLAUDE.md か rules の 1 行で足りる)

`disable-model-invocation: true` は、**リモートや公開状態を書き換える操作にだけ**付ける
(push、タグ、デプロイ)。ローカルで取り消せる操作に付けると、モデルが呼び出しを拒否されて
作業ごと放棄する事故が起きる (実測で成功率 -71pt)。

## .claude/agents/ — サブエージェント

**長い出力や大量調査を親コンテキストから切り離す価値が明確なときだけ。**

実測では、小〜中規模のタスクで呼ばれると成功率は変わらず $ +35% / 実時間 +56% / tool call 2 倍。
既定は**作らない**。

作ってよい条件:

- 出力が明らかに長い (数百件のテスト結果、大規模な横断調査、大量ログの絞り込み)
- 親が結論だけ受け取れば済む
- description に**規模の条件**を書ける (「小さいものは直接調べた方が速い」と明示する)

小規模な作業用 Agent は作らない。

## .claude/settings.json — 権限とフック

**プロジェクト固有の permission / deny / hook が必要なときだけ。**

入れる価値があるもの:

- `permissions.deny` — このリポジトリ固有の読ませたくないパス
  (`application-prod*.yml`, `*.tfvars`, `appsettings.Production.json`, 本番接続情報)
- `permissions.allow` — このリポジトリでよく使う安全なコマンド (`Bash(./gradlew test:*)` など)
- `hooks` — リポジトリ固有のセットアップ (Claude Code on the web 用の SessionStart など)

入れない:

- 個人設定と会社共通設定に既にある deny / allow
- 個人の好み (テーマ、モデル、通知)。git 管理下に入るファイルなので混ぜない

deny だけで済むならそれだけ書く。**空の `permissions` を持つ settings.json は作らない。**

## 既存 `.claude/` がある場合

各ファイルを次のいずれかに分類して提示する。勝手に消さない・上書きしない。

| 判断 | 条件 |
| --- | --- |
| 維持 | 上の関門を通る。触らない |
| 修正提案 | 有効だが一般論が混ざっている / 古い。差分を提示する |
| 統合 | CLAUDE.md と rules で重複している。片方に寄せる案を出す |
| 削除候補 | 関門 1〜3 に当たる (一般論、コードで分かる、上位設定と重複)。**理由を添えて提案するだけ** |
