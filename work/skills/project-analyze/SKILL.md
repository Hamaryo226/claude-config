# 既存プロジェクトを解析して設定を作る

引き継いだ／既に動いている業務システムのリポジトリで実行する。
コードだけでなく設計書・CI・テストまで読み、**そのリポジトリを見ないと分からないことだけ**を設定に落とす。

`/onboard` との違い: onboard は雛形を素早く置くための軽い手順。こちらは
**設計資料と実装の突き合わせ**まで行い、層 (CLAUDE.md / rules / skills / agents / settings) の
振り分けまで判断する。時間はかかる。

## この Skill の前提 (最重要)

**設定ファイルを作ることは成果ではない。** 実測 (`eval/results/*/CONFIG-REVIEW.md`) で分かっていること:

- 効果が確認できたのは、常時読み込みの環境固有ルールと、狭くスコープした表記ルールだけ
- 一般論を足すと、同じファイルにある効く指示の追従率が下がる
- 使いどころの狭くない Skill / Agent は、成功率を上げずに token・時間・tool call だけ増やす

したがって **「作らない」という結論を出して終わってよい。** 迷ったら作らない。
判断の基準は [references/decision.md](references/decision.md) にある。**Phase 2 に入る前に必ず読むこと。**

## 進め方

### Phase 0. 棚卸し

```bash
ls -a
cat CLAUDE.md AGENTS.md .claude/CLAUDE.md 2>/dev/null
ls -R .claude 2>/dev/null
```

- 既存の `CLAUDE.md` / `.claude/` があるなら、**この時点では何も変えない**。中身を読んで Phase 2 に持ち込む
- `AGENTS.md` があって `CLAUDE.md` が無いなら、`@AGENTS.md` を 1 行目に書いた `CLAUDE.md` を作る案を持つ
  (Windows ではシンボリックリンクを使わない)
- ユーザーの `~/.claude` と会社共通設定に既にあることは、**このリポジトリの設定に書かない**。
  重複させると常時トークンを二重に使ううえ、片方だけ直して食い違う

### Phase 1. Discover

[references/discovery.md](references/discovery.md) の項目を順に埋める。**推測で埋めない。**
読んだファイルのパスを控える。

PDF は Read ツールで読み、10 ページを超える場合はページ範囲を分ける。
Read ツールが対応しない形式 (`.xlsx` / `.docx` / `.vsdx` など) は、利用可能な変換手段があれば
読み取り専用で抽出する。安全に読めなければ「存在するが未解析」として一覧に残し、中身を推測しない。

情報が矛盾したときの優先順位:

1. 明示された最新の仕様・設計資料
2. CI / build 設定
3. 実装コード
4. テスト
5. README 等
6. git 履歴

**設計書が古いのか実装が逸脱したのか判断できない場合は、どちらかを正解に決めない。**
矛盾として Phase 2 の報告に残し、設定には書かない (書くなら「未確定」と明記して書く)。

### Phase 2. Design — 計画を提示する

**ここでファイルを書き始めない。** 次の形で計画を提示する。

```
## 生成計画

CLAUDE.md: 必要 / 不要
  理由:
  根拠ファイル:

.claude/rules/<name>.md: 必要 / 不要
  paths:
  理由 (なぜ常時ではなく条件付きか):
  根拠ファイル:

.claude/skills/<name>/: 必要 / 不要
  理由 (どの複数ステップ作業が何回繰り返されるか):
  根拠ファイル:

.claude/agents/<name>.md: 必要 / 不要
  理由 (親コンテキストから切り離す価値が何か):

.claude/settings.json: 必要 / 不要
  理由 (個人・会社共通設定と重複しないか):

## 作らないと判断したもの
  <候補> — <理由>

## 見つかった矛盾 (設定には書かない)
  <設計書 X の記述> vs <実装 Y> — どちらが正しいか未確認

## 未解析
  <バイナリ設計書のパス>

## 既存 .claude/ の扱い
  <ファイル> — 維持 / 修正提案 / 統合 / 削除候補 + 理由
```

判断の根拠は [references/decision.md](references/decision.md) に従う。
**「作らない」が並ぶ計画は正しい成果物。**

ユーザーが今回の依頼で設定の生成・改善まで明示している場合は、計画を会話に残して Phase 3 へ進む。
分析または提案だけを求められた場合は、ここで止める。次のどれかに当たる場合も確認を待つ:

- 既存設定と根拠資料が矛盾し、どちらを採用するかで挙動が変わる
- 既存ファイルの大部分を置き換える必要がある
- 依頼範囲を超える生成が必要になる

### Phase 3. Generate

生成・改善まで依頼されている範囲だけを書く。テンプレートと分量の上限は
[references/templates.md](references/templates.md) を必要になった時点で読む。

- **既存ファイルを丸ごと置き換えない。** 明示された改善依頼の範囲で最小差分を適用する。
  判断が分かれる変更だけ確認する
- 同じルールを CLAUDE.md と rules の両方に書かない。全体に効くものは CLAUDE.md に 1 回だけ
- 根拠を追えるようにする。Phase 2 の計画 (根拠ファイル付き) をそのまま会話に残す。
  ユーザーが保存を望んだときだけ `.claude/PROJECT-ANALYZE.md` に落とす (自動では作らない)

### Phase 4. 検証

書いたコマンドは**実際に走らせて確かめる。** 走らせられないもの (本番接続、社内ネットワーク必須など) は
`CLAUDE.md` に「未確認」と明記する。確認していないコマンドを断定形で書かない。

コミットはしない。必要ならユーザーに `/commit` を使ってもらう。

## 守ること

- 一般的なプログラミングのベストプラクティスを書かない。Sonnet 5 は既に知っている
- コードだけを見てアーキテクチャを推測して書かない。設計資料か CI で裏を取る
- 設計書に書いてあるという理由だけで正しいと扱わない
- 生成物の分量を増やす方向の判断をしない。迷ったら削る
- `.claude/settings.local.json` は個人用なので、この Skill では作らない
