# システム変更を安全に実装する

`$ARGUMENTS` を完了条件として扱い、既存の未コミット変更を保護しながら実装する。
単純な 1 ファイル修正では使わない。API、DB、バッチ、画面、外部連携など複数の境界に
影響しうる変更で使う。

## 1. 変更境界を決める

- リポジトリの `CLAUDE.md` / `AGENTS.md` と現在の `git status` を先に確認する
- 要求を観測可能な完了条件に直す。仕様書やチケットがあれば根拠をファイル名と節で残す
- 不明点は、実装結果を大きく変えるものだけ確認する。それ以外は仮定を明示して進める
- 依頼外のリファクタリング、依存更新、全体整形を変更範囲に入れない

## 2. 必要な範囲だけ追跡する

変更対象から次の境界を外向きにたどる。該当しない境界は調べない。

- 呼び出し元と公開契約: API、DTO、イベント、ファイル形式、CLI
- 永続化: schema、migration、既存データ、transaction、rollback
- 横断要件: 認可、監査、個人情報、ログ、エラー処理
- 運用: 設定、バッチ、監視、デプロイ順、後方互換性
- 検証: 既存テスト、CI、関連ドキュメント

大きな変更なら、編集前に「変更するもの / 変更しないもの / 未確認」を短く提示する。

## 3. 実装する

- 既存の設計、命名、エラー処理、テスト配置に合わせて最小差分で実装する
- 契約やデータ形式を変える場合は、互換性または移行手順を同じ変更に含める
- 認証情報、顧客データ、実ログを外部検索へ出さない
- 本番適用、デプロイ、DB migration の実行は行わない。必要なコマンドだけ提示する

## 4. 検証して閉じる

1. 変更箇所に最も近いテストまたは再現手順
2. 対象モジュールの build / lint / typecheck
3. 実行可能なら CI 相当のチェック
4. `git diff` と `git status` で、依頼外の差分と生成物が無いことを確認

最後に、完了条件ごとの結果、実行したコマンド、未確認事項、残るリスクを報告する。
build やテスト成功を、画面・外部連携・本番動作の確認済みという意味に広げない。
