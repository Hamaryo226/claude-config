# 変更を検証する

`$ARGUMENTS` があれば最優先の完了条件として扱う。コードは原則変更せず、失敗を見つけたら
原因と修正候補を報告する。明示的に修正まで頼まれた場合だけ編集する。

## 1. 差分から検証対象を作る

- `git status`、staged / unstaged の `git diff`、関連するリポジトリ指示を確認する
- 各変更を、要求・公開契約・データ・設定・UI・運用・ドキュメントのどれに効くか分類する
- 変更していないユーザー作業を検証対象やコミット対象に混ぜない

次の 3 列を短く組み立てる。

| 完了条件 | 確認方法 | 実行可否 |
| --- | --- | --- |
| 何が成立すべきか | テスト、build、静的確認、実動作 | 今回実行 / 人が確認 / 環境不足 |

## 2. 狭い確認から実行する

1. 変更箇所に最も近い既存テストまたは再現手順
2. 影響モジュールの lint / typecheck / build / test
3. 必要かつ実行可能な場合だけ全体チェック

- コマンドは `package.json`、wrapper、solution、CI 定義など実リポジトリから決める
- テストを通すために期待値や検証を弱めない
- 依存の追加、外部環境、本番、デプロイ、DB 変更が要る確認は自動実行しない
- 失敗が環境要因かコード要因かを分け、同じ失敗を無目的に繰り返さない

## 3. 差分を監査する

- `git diff --check` と最終 `git status` を確認する
- 要求に対応しない差分、デバッグ出力、秘密情報、生成物、意図しない契約変更を探す
- 自動整形が非同期なら、完了後の差分を改めて読む

## 報告

- **合格:** 実行した確認と結果
- **不合格:** 最初の本質的な失敗、原因箇所、再現コマンド
- **未確認:** UI、外部連携、権限、実データ、本番など今回確認できないもの
- **差分範囲:** 意図したファイルだけか、既存のユーザー変更が残っているか

「未確認」が 1 件でもある場合、全体を「動作確認済み」と表現しない。
