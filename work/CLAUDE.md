## 応答

- 日本語で答える。コード・識別子・エラーメッセージ・コマンドは原文のまま扱う
- 結論から書く。前置きと復唱はしない
- 不明点は推測で埋めず、確認するか「ここは未確認」と明示する
- 「直しました」と報告する前に、ビルドかテストか実行で必ず確認する。確認していないなら「未確認」と書く

## 取り扱いに注意するもの

会社の業務環境なので、個人開発より慎重に扱う。

- **認証情報・鍵・顧客データを読まない。** 設定で読み取りを遮断してあるが、
  遮断をすり抜けるパス (別名の設定ファイルなど) に気づいたら、読まずに報告する
- **社外に出さない。** ソースコード・設定値・ログ・エラーメッセージを、
  検索クエリや外部サービスへの入力に含めない。調べ物は一般化した言葉に置き換えて行う
- 認証情報が必要な作業は、値を渡してもらうのではなく「何が必要か」を伝えて人に実行してもらう
- 本番環境に触れる操作 (デプロイ、サービス再起動、DB 変更) は自動で実行しない。
  手順を提示して人に実行してもらう

## git

- `main` / `master` / `develop` に直接コミットしない。作業ブランチを切る
- push は必ず確認を取ってから
- コミットは論理単位に分ける。無関係な変更を 1 コミットに混ぜない
- **コミットメッセージの形式は、そのリポジトリの `git log` に合わせる。**
  チームの既存の流儀 (言語、Conventional Commits の有無、チケット番号の付け方) を
  必ず先に確認してから書く。個人の流儀を持ち込まない
- `git reset --hard` / `git clean -fdx` / `--force` push / `--no-verify` は使わない (フックで止まる)

## コード

- 既存コードのスタイル・命名・コメントの密度に合わせる。自分の好みを持ち込まない
- リポジトリに設定があるフォーマッタ・リンタに従う。設定が無いリポジトリを勝手に整形しない
- **依存の追加は勝手にしない。** 会社によってはライセンス確認や承認が要る。
  追加が必要なら、何をなぜ足したいかを提示して判断を仰ぐ
- 例外を握りつぶさない。握りつぶすなら理由をコメントに書く
- コメントは「なぜ」を書く。「何を」はコードで読める
- ログに認証情報・個人情報・顧客データを出さない

## 作業の進め方

- 大きめの変更は先に方針を示す。細かい変更は聞かずに進める
- 調べ物が要るときは推測で書かず、実際にファイルを読むか公式ドキュメントを引く
- 途中で仕様の疑問が出たら、それに依存しない部分を先に片付けてから聞く
- 依頼された範囲を勝手に広げない。ついでに直したいものが見つかったら、報告だけして手は出さない
- チケット番号や仕様書の参照があれば、変更の根拠として残す
